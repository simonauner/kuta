# Kuta

Kuta är en Strava-liknande löparapp: ladda upp pass från Garmin (FIT) eller logga manuellt, följ statistik över tid (puls, fart, max distans), logga skor per pass, få rekord ("snabbaste 5k", "snabbaste 5k i år"), och följ andra löpare med flöde, profiler och grupper. Svenskt namn, ska funka internationellt. Webbapp som PWA (sparas till hemskärmen) – ingen App Store i början.

## Arbetsflöde
- Håll bestående projektregler i `AGENTS.md`, körinstruktioner i `README.md` och återanvändbara agentprocedurer i `.agents/skills/`. Uppdatera berörd dokumentation när ett arbetssätt eller beslut ändras; undvik ändringsloggar och dubblerade instruktioner.
- Använd [run-dev](.agents/skills/run-dev/SKILL.md) för att starta appen och verifiera flöden lokalt. Använd syntetiska konton och data. Andra worktrees delar maskin och Docker: välj en egen ledig portserie för en ny miljö, stoppa bara egna processer med deras PID och rör inte andras containrar, volymer eller git stash.
- Verifiera ändrat beteende enligt testnivåerna nedan, och kontrollera ändrade flöden i webbläsaren. Kontrollera att privata pass inte kan läsas eller ändras av en annan användare när åtkomstlogik ändras.
- Före commit av applikationskod: kör `npm run verify` i `web/` (samma kontroller som CI) med Node-versionen i `.nvmrc` och `dotnet test --project api/Kuta.Api.Tests` mot lokal Supabase. Testerna använder standardinstansen, eller den egna instansen med `KUTA_PORTS=BAS` (samma BAS som `run-dev.sh --ports`); kör mot en egen instans i stället för att ändra eller återställa en lånad miljö. Redovisa om de inte kunnat köras. För enbart dokumentation eller instruktioner räcker granskning av diff, lokala länkar och beskrivna kommandon mot implementationen.
- Redovisa vad som verifierats, resultatet och miljön/versionen som kontrollerats. En pågående kontroll är inte godkänd. Återanvänd tidigare resultat bara om relevanta kod-, test- och konfigurationsunderlag är oförändrade.
- Ändra inte hostad databas, hemligheter eller driftsättning om uppgiften inte omfattar just den åtgärden. Verifiering sker lokalt; en instruktion om att testa innebär inte en instruktion om att deploya.

## Testnivåer
- Välj före varje nytt test den lägsta nivå som kan upptäcka felet. Ett test ska skydda en beteenderegel eller den egna nivåns ansvar; fler fall som kör samma gren ger inte mer skydd. Välj fall vid gränser och där beteendet skiljer sig.
- **Enhet:** beräkningar, parsning, format, validering och presentation testas direkt mot funktionen eller klassen, utan appserver, databas, nätverk eller mejl. Exempel: rekordmotorns distanser, pauser och trasiga mätvärden hör hemma här. Om ren logik sitter i en endpoint eller komponent, bryt ut just den logiken när den behöver testas; bygg inget generellt lager för testernas skull.
- **Databas/integration:** SQL, transaktioner, constraints, lagring och användaråtkomst testas mot riktig lokal Postgres/Supabase på den lägsta kodnivå som äger regeln. Ersätt inte databasregler med mockar eller en minnesdatabas. Kontrollera med två användare att den ena varken kan läsa eller ändra den andras privata pass.
- **HTTP:** testa kopplingen mellan lagren och HTTP-ansvaret: routing, bindning, statuskoder, svarskontrakt, autentisering och CSRF. Behåll ett representativt huvudflöde per endpoint; upprepa inte beräknings-, parser- eller valideringsmatriser som redan täcks längre ned. Gemensamma säkerhetsregler testas där de tillämpas gemensamt, utan samma matris för varje endpoint; featurespecifik åtkomst måste fortfarande verifieras.
- **Webbläsare:** verifiera användarflöden, navigering och sådant som kräver riktig rendering eller webbläsarbeteende. Lägg automatiska fall här bara när en lägre nivå inte kan visa regeln; testa exempelvis inte tempoformler eller varje ogiltigt inmatningsvärde genom hela appen.
- Skapa testdata under nivån som testas. Enhets- och databastester ska inte registrera konton via HTTP eller vänta på Mailpit. Ett HTTP-test får använda lägre nivåer för förberedelser; kör registrering, mejlbekräftelse och FIT-uppladdning som förberedelse bara när just det flödet är föremålet för testet. Återanvänd små befintliga testhjälpare innan nya införs.
- När ett befintligt test berörs av en ändring, flytta ned fall som ligger för högt och ta bort dubbleringen med bibehållet skydd. Motivera i PR-beskrivningen varför nya HTTP- eller webbläsartester behöver den nivån och vad de tillför utöver lägre tester.

## Stack (beslutad)
- **API:** .NET 10, ASP.NET Core minimal API, **Dapper** (inte EF Core), Npgsql, Postgres + PostGIS, NetTopologySuite.
- **Supabase:** hanterad Postgres (Stockholm/ARN, Sverige) och **Supabase Auth**. Inloggningen går via vårt API (BFF): API:t pratar med Supabase Auth och lägger sessionen i en krypterad HttpOnly-cookie, så tokens aldrig når JavaScript. Webben använder varken supabase-js eller Supabases Data API och behöver inga Supabase-nycklar. Lokalt håller sig allt till 553xx: webben 55300 (preview 55301), API:t 55302, Supabase 55320–55329 (se `supabase/config.toml`). Starta allt med `scripts/run-dev.sh`; `--ports BAS` kör en extra instans med egen Supabase-stack (se README).
- **Migreringar:** DbUp med inbäddade SQL-filer i `api/Kuta.Api/Migrations/`.
- **Web:** React + Vite + TypeScript, TanStack Router (kodbaserad) + Query, Tailwind v4, shadcn/ui (components.json finns, komponenter läggs till med `npx shadcn@latest add ...`), Motion för animationer, vite-plugin-pwa, MapLibre GL.
- **Filer:** Cloudflare R2 (S3-kompatibelt) för rå-FIT-filer och PMTiles-kartor. `activities.raw_file_key` pekar på objektnyckeln.
- **Jobb/köer:** egen kö i Postgres (`jobs`, `JobQueue`, `JobWorker`) med `for update skip locked` och förnyat lås, inte Redis/RabbitMQ och inte Hangfire/Wolverine (Hangfire sparar undantagstexter, vilket strider mot den privata loggningen). Nya långa jobb läggs till som en ny `kind`. E-post och web push kommer senare.
- **FIT-parsning:** Garmins officiella C#-SDK (NuGet `Garmin.FIT.Sdk`).

## Status
- `web/`: statisk publik startsida på `/`, React-appen på `/app` med Flöde/Pass/Statistik/Profil (se README för dokument och sökvägar). Inställningar på `/app/settings` nås via kugghjulet på Profil och innehåller språkval, pulssamtycke, Strava-import, dataexport, e-postadress, utloggning och Danger zone för att radera alla pass eller kontot. Profil visar löparens namn och egna pass; Pass länkar till Skapa ny aktivitet för FIT-uppladdning och manuell registrering; filmodalen och Inställningar visar samma checkbox för pulssamtycke, även när samtycket redan är givet. Bottennavigering, sidövergångar och PWA-manifest. Appikoner finns som PNG (192/512, maskable 512 och apple-touch-icon 180), med SVG-underlag i `web/public/brand/`.
- `api/`: bygger och körs mot lokal Supabase; `/api/health` svarar med PostGIS-version. Paketversioner pinnade. Namnmatchning snake_case→PascalCase är satt via `DefaultTypeMap.MatchNamesWithUnderscores`.
- Auth (`SupabaseAuthClient`/`SupabaseCookieSession`):
  - `POST /api/auth/signup|login|logout` (registreringen kräver godkända användarvillkor `/terms` och integritetspolicy `/privacy`; version och tidpunkt i `users.terms_version`/`terms_accepted_at`, se README), `GET /api/auth/confirm?token_hash=` (länken i bekräftelsemejlet, mall i `supabase/templates/confirmation.html`; bekräftar bara adressen och skickar till inloggningen, så att en länk till någon annans konto inte loggar in den som klickar), `GET /api/antiforgery`.
  - Alla skrivande `/api`-anrop kräver `X-CSRF-TOKEN` från `GET /api/antiforgery`. Token är knuten till användaren: hämta en ny efter in- och utloggning.
  - Sessioner i `user_sessions` (kontrolleras vid varje anrop, utloggning slår igenom direkt). Cookien glider 30 dagar, hård gräns 180 dagar. Access-token förnyas strax före utgång; Supabase tillfrågas om återkallelse högst var 5:e minut.
  - Data Protection-nycklar i `data_protection_keys`. Rate limit 10 auth-anrop/5 min/IP (IPv6 per /64-nät), och inloggning/återställning högst 10 försök/15 min/e-postadress.
  - `users` är en profiltabell med samma id som `auth.users` (FK, kaskadradering). `GET /api/me` ger id, e-post och `displayName` (null tills profilen skapats); `PUT /api/me` skapar/uppdaterar profilen.
    - Webben: `src/lib/api.ts` (fetch med CSRF-token, `ApiError` från API:ts `{ error }`), `src/lib/auth.ts` (`meQuery`, null = utloggad), `src/routes/auth.tsx` (inloggning/registrering/kolla e-post, namnval första gången). `Layout` visar inloggningen i stället för appen när `me` är null. Fel från API:t har formen `{ "error": "...", "code": "..." }`; webben översätter koden till valt språk.
  - PWA:ns navigeringsfallback får bara svara på appens sökvägar under `/app` (`navigateFallbackAllowlist` i `vite.config.ts`), aldrig på startsidan eller `/api/` – annars når bekräftelselänken aldrig API:t.
  - Lösenordsåterställning: `POST /api/auth/recover`, mejllänk till `GET /api/auth/reset-password?token_hash=`, sedan `POST /api/auth/reset-password`. Separat krypterad HttpOnly-cookie (högst 15 minuter), engångsanvändning via `user_sessions`; ger ingen appåtkomst. Lyckat byte avslutar kontots Kuta-sessioner. Mall och driftinställning finns i README.
  - Sessionsrensning: migrering 019 tar timvis bort rader 30 dagar efter första registrerade avslut/absoluta utgång. Lokalt verifierad och aktiverad i drift (se README). Jobbet kräver att databasen är i drift; cookiens inaktivitetsgräns sätter inte `ended_at`.
  - Captcha (Cloudflare Turnstile) är på i hostad Supabase Auth och stoppar direktanrop med den publika nyckeln. API:t går förbi den med `Supabase__SecretKey`, som därför måste finnas i drift. IP Address Forwarding är på, så att Supabase räknar sina gränser per besökare (se README).
  - Turnstile i Kutas egna formulär (`TurnstileVerifier`, `components/turnstile.tsx`): registrering och glömt lösenord kräver en token som API:t kontrollerar mot Cloudflare innan Supabase anropas. Webben hämtar site key från `GET /api/turnstile`; utan både `Turnstile__SiteKey` och `Turnstile__SecretKey` (lokalt, i tester) är kontrollen av och inget laddas från Cloudflare. CSP:n tillåter `challenges.cloudflare.com` för script och frame i hela appen.
  - Saknas: MFA, inloggning med Google/Apple, logga ut andra sessioner.
  - Lokalt: kommer bekräftelsemejlet i Mailpit (http://127.0.0.1:55324) med Supabases engelska standardmall har auth-containern startat före Kong – kör `docker restart supabase_auth_kuta`.
- FIT-uppladdning (`ActivityEndpoints`, `FitImport`, `RawFileStore`):
  - `POST /api/activities` (multipart, fältet `file`, högst 20 MB och 500 000 mätpunkter, valfria `title` och `sport`) tolkar filen med `Garmin.FIT.Sdk` (alla sessioner + records) och skriver `activities` + `activity_streams` i en transaktion; rutten förenklas med Douglas-Peucker (~5 m). Samma fil igen ger 409 (`raw_file_sha256` unik per användare). `POST /api/activities/preview` tolkar samma fil utan att spara något (förifyller formuläret; puls bara med samtycke). Uppladdning, förhandsvisning och Strava-import delar rate limiten `uploads`: 30 anrop/5 min/användare.
  - `POST /api/activities/manual` (JSON) skapar ett pass utan fil (`source = 'manual'`): sport, titel, start, tid, distans, höjdmeter och snittpuls (bara med samtycke). Inga tidsserier eller rekord. Validering i `ActivityInput`.
  - **Pulssamtycke:** `PUT`/`DELETE /api/me/hr-consent`, `users.hr_consent_at`, `hrConsent` i `/api/me`. Utan samtycke sparas varken puls eller råfil (råfilen innehåller puls). Återkallat samtycke raderar all sparad puls och alla råfiler. Ett pass uppladdat utan samtycke får puls bara om det tas bort och laddas upp igen (annars är det en dubblett).
  - `DELETE /api/activities/{id}` tar bort ett eget pass (tidsserier via kaskad) och dess råfil; någon annans pass ger 404. Råfilen raderas först. Webben har "Ta bort" med bekräftelse i passlistan.
  - `DELETE /api/me` (JSON `{ password }`, kontrolleras mot Supabase; auth-rate limiten) raderar det egna kontot: råfiler först under samma profillås som importen, sedan `auth.users` i samma databastransaktion. Kaskadradering tar bort profil, utrustning, pass och Supabase-/Kuta-sessioner; sessionscookien rensas. Inställningarnas Danger zone kräver lösenordet för kontoradering.
  - `DELETE /api/activities` raderar alla egna pass, tidsserier, rekord och råfiler. Inställningarnas Danger zone kräver ett slumpat löparord i en bekräftelsemodal; kontot och inställningarna behålls.
  - Råfiler via S3-protokollet (`Storage__ServiceUrl/Region/Bucket/AccessKeyId/SecretAccessKey`): lokalt Supabase Storage (bucket `fit-files` i `supabase/config.toml`), i drift R2 eller Supabase Storage.
  - Webben: passlistan (`routes/activities.tsx`) med knappen "Skapa ny aktivitet" till `/app/activities/new` (`routes/new-activity.tsx`): fyll i passet manuellt, eller välj en FIT-fil via "Ladda upp fil" (modal med checkbox för pulssamtycke) som fyller i fälten. Modalen varnar och räknar upp ifyllda fält som filen skriver över; titeln behålls. Passet har en valfri beskrivning (högst 10 000 tecken), som behålls när en fil väljs och visas med radbrytningar på passsidan. Från en fil går titel, beskrivning, sport, taggar och utrustning att ändra; mätvärdena är låsta eftersom tidsserierna, splits och rekord bygger på dem.
  - Pulssamtycke och Strava-import finns på Inställningar (`routes/settings.tsx`).
  - Nya sökvägar i appen måste också läggas till i listan över appens sökvägar i `Program.cs` (och i `WebRoutingTests`); annars ger direktlänk och omladdning 404 i drift, fast det fungerar i Vites dev-server.
  - Passsidan `/app/activities/$activityId` (`routes/activity.tsx`, laddas vid behov) visar ett pass från `GET /api/activities/{id}` (eget eller delat pass enligt läsregeln; med tidsserier som filtreras för andra än ägaren): titel, statistik, karta, diagram (höjd, tempo, puls) och splits per km. Titeln är egen eller sport + tid på dygnet (`lib/activity.ts`, med tester i `web/tests/activity.test.mjs`).
  - Karta: MapLibre med kartbilder från OpenFreeMap (ingen nyckel; leverantören ser ungefär var passet gick). `tiles.openfreemap.org` är tillagt i CSP:n; workern pekas ut med `setWorkerUrl`. Planen är egen PMTiles när ruttdata ska stanna hos Kuta. Diagram: uPlot.

Varvens puls följer samma samtycke som övrig puls. Passsidan visar snittkadens, snittemperatur, diagram för båda och en utfällbar, höjdanimerad varvpanel ovanför kartan med begränsad höjd och egen scroll. Pass uppladdade före 007 har inget av detta.

- Dolda platser: Inställningar länkar till `/app/settings/privacy-places` med brödsmulan Profil → Inställningar → Dolda platser. Där kan användaren hantera flera privata kartpunkter med namn och radie, exempelvis Hem och Arbetsplats. Maskering sker i svaret till andra mottagare utifrån aktuella platser, även för äldre pass. Delade kartminiatyrer döljer också minst 500 m runt start och mål. Ägaren och egen export behåller originalrutten. Platser ingår i export och kaskadraderas med kontot. Se README.
- Multisport: FIT med flera sessioner importeras som ett samlat triathlon-, swimrun- eller multisportpass. `activity_parts` (migrering 013) bevarar originaldelar och en separat redigerad uppdelning; tidsserier och råfil ändras aldrig av redigering. Uppdelningsverktyget finns bara på skapa- och redigeringssidan, med förhandsvisning och sidans gemensamma Spara/Avbryt. Skapa skickar `parts` som JSON i FIT-formuläret; redigera skickar `multisport` eller `restoreParts` tillsammans med övriga ändringar i `PUT /api/activities/{id}`. Passsidan visar delarna och låter användaren välja del för karta/diagram/statistik. Delar måste täcka inspelningen utan luckor/överlapp, högst 200 delar. Rekord beräknas inom varje löpdel och korsar aldrig andra sporter. Utrustningsanvändning räknas bara för markerade delar. Månadsstatistik per sport räknar relevanta delar; totalen räknar passet en gång. Hela kort är valbara, reglagen följer sportfärgen och infogning/sammanslagning animerar höjden med hänsyn till minskad rörelse. Återställning kräver bekräftelse och sparas med formuläret. Se README för detaljer.
- Utrustning: `equipment` med typen `shoe` från start (migrering 009 ersätter `shoes`). `activity_equipment` kopplar flera utrustningsdelar till pass och säkerställer samma ägare via FK. Total distans och förfluten tid inklusive pauser räknas direkt från passen plus tidigare användning; se README. Inställningar länkar till `/app/settings/equipment`, där utrustning skapas, redigeras i samma modal, pensioneras, återaktiveras och raderas samt visar totaler. Sidan använder shadcn/ui Breadcrumb (Base UI) med Profil → Inställningar → Utrustning. Passformuläret visar aktiva skor med senast använda aktiva sko som förval och ”Ingen sko”; ”Skapa ny” på etikettraden öppnar en modal och väljer skon efter sparande. API:t använder `/api/equipment` och `equipmentIds`, även för FIT, och avvisar pensionerad utrustning på nya pass. Pensionering behåller historiken; radering tar bort länkarna men behåller passen. Passsidan visar bara kopplad utrustning och valda taggar som etiketter. Knappen Redigera aktivitet öppnar `/app/activities/$activityId/edit` med gemensamma Spara och Avbryt för titel, beskrivning, taggar och utrustning, som sparas tillsammans via `PUT /api/activities/{id}`; utrustningskopplingar kan även omfatta historiska pensionerade skor. Utrustningsväljaren visar checkboxar för högst tre tillgängliga alternativ och en dropdown med flerval för fler.
- Aktivitetstaggar: `activities.tags text[]` med GIN-index (migrering 008). Tillåtna nycklar i `ActivityInput.Tags`; webben hämtar listan via `/api/activity-tags` och översätter `tagNames`. Taggar väljs vid skapande och ändras på den gemensamma redigeringssidan via `PUT /api/activities/{id}`. Passlista och rekord stöder `?tag=race` (se README).
- Statistik över tid: `/app/stats` visar årsöversikt med antal pass, distans, träningstid och månadsdiagram/tabell för distans, tid, tempo och puls. År och sportgrupp kan väljas (förval: innevarande år och löpning). `GET /api/activities/statistics` summerar alla egna pass i Postgres i vald tidszon, med tidsvägd puls och distansvägt tempo; saknade mätvärden visas som `–`. År för år jämför ackumulerad mängd per år till samma datum via `GET /api/activities/statistics/days` (dagssummor; samma SQL-regler som målen i `SportGroups.EffectiveCte`). API-kontrakt och beräkningsregler finns i README.
- Träningsbelastning (`TrainingLoad`, `TrainingLoads`, migrering 019): fartbaserad rTSS för löpning mot tröskelfart (egen eller ur VDOT), med backar justerade enligt Minettis kostnadskurva,, kondition/trötthet/form med 42/7 dagar på Statistik och varning på Pass när konditionen ökar mer än 7 per vecka. `activities.run_intensity` räknas i samma omberäkning som rekorden. Se README.
- Rekordmotor (`BestEffortCalculator`, `BestEfforts`, `BestEffortEndpoints`): FIT- och Strava-importen sparar bästa insatser för löpning i samma transaktion som passet. Glidande fönster med linjär interpolering och förfluten tid inklusive pauser; trasiga värden och återställd tid/distans bryter strömmen. `GET /api/activities/{id}/best-efforts`, `GET /api/records?year=2026` (utelämnat år = personbästa), `POST /api/activities/{id}/best-efforts/recalculate` (CSRF), `GET /api/records/trend?distanceM=` (månadsbästa och rekordhistorik) och `GET /api/records/predictions` (VDOT enligt Daniels/Gilbert från starkaste insatsen ≥ 5 km de senaste 90 dagarna). Statistiksidan visar rekord, utveckling och prognos. Bara egna pass. Rekord väljs direkt ur `best_efforts`, så radering kräver ingen separat rekorduppdatering. Exakta distanser, UTC-årsurval och omberäkning av äldre pass beskrivs i README. Beräkningstester och integrationstester med syntetiska FIT-filer finns; verifiering med riktiga klockfiler återstår.
- Strava-arkiv (`StravaImport`, `StravaImportEndpoint`): `POST /api/activities/import/strava` tar ZIP (högst 500 MB), sparar arkivet på lokal disk och köar ett jobb som läser `activities.csv` och FIT/GPX (även gzip); pass utan fil får CSV-sammanfattning. Namn, beskrivning (`Activity Description`), sport, datum och SI-sammanfattningar kommer från CSV, tidsserier från filen. Dubbletter hoppas över per användare via Strava-ID eller råfilshash. Pass följer användarens standardsynlighet; puls och råfiler kräver samtycke, som kontrolleras för varje pass. Samtyckesåterkallelse och import låser samma profilrad. Resultatet räknar importerade/dubbletter och listar misslyckade Strava-ID:n; avbruten import kan köras igen. Skor importeras först via `StravaEquipment` och kopplas via Stravas Gear-ID (migrering 011). Statistik räknas från passen, med noll i startvärden. Återimport bevarar ändrade skor och kompletterar bara pass utan utrustning; historiska pass får använda pensionerade skor. `shoes.csv` saknar ID:n: bara skor som refereras från pass kan importeras. Resultatet räknar även importerade skor och kompletterade pass. Foton, kontakter, privata anteckningar och cyklar importeras inte. Gränser och användning finns i README.

## Designbeslut att hålla fast vid
- **Tidsserier som arrayer** i `activity_streams` (en rad per pass), inte en rad per sekund.
- **Importen är en idempotent pipeline:** spara rå fil → parsa → sammanfattning + förenklad rutt (Douglas-Peucker) → bästa insatser per standarddistans (1 km, 1 mile, 5k, 10k, halvmara, mara) → uppdatera personbästa. Ska gå att köra om vid ändrad logik. "Snabbaste 5k i år" är en query över `best_efforts`.
- **Garmin Connect:** manuell FIT-uppladdning finns. Den officiella anslutningen är byggd (se README, Garmin Connect) och kräver `Garmin__ClientId`/`Garmin__ClientSecret` i drift. Före lansering kan bara konton i `Garmin__AllowedUserIds` ansluta; sätt `Garmin__OpenToAll` först när integritetspolicyn beskriver anslutningen som tillgänglig och Garmins 30-dagarsfrist för visning gått ut (tidigast 2026-12-01). Garmin beskriver Starter Access med push, högst 1 000 anslutna användare och utan historik i [utvecklarportalen](https://developerportal.garmin.com/developer-programs/connect-developer-api) (kontrollerat 2026-11-01); utgå inte från den tidigare uppgiften om pausade ansökningar. Inga inofficiella Garmin-scrapers.
  - Åtkomst till utvecklarprogrammet finns (2026-11-01). Avtal, dokumentation och nycklar är konfidentiella: nycklar bara i 1Password, inga Garmin-dokument eller avtalstext i repot.
  - Före första riktiga anslutning: användarvillkor med skydd för Garmin och sätt att anmäla missbruk, integritetspolicy som beskriver Garmin-datan, samtycke med "Koppla från Garmin" som raderar datan och hanterar Garmins avregistrering, och redovisning av alla leverantörer som hanterar datan (Fly, Supabase, R2). Garmin-pass på kartan kräver egna PMTiles eller att OpenFreeMap redovisas, eftersom kartbilderna avslöjar ungefärlig plats.
  - Bara Garmins OAuth och data via egen endpoint på kutaapp.com; aldrig Garmin-lösenord, aldrig vidare till tredje part. Skriv inte tillbaka ändrad data till Garmin. Frånkoppling (i Kuta eller hos Garmin) och kontoradering avregistrerar hos Garmin och raderar allt som hämtats därifrån. Garmin-pass är privata via constraint (migrering 025) tills Garmin godkänt visning för andra; ta då bort constraintet och uppdatera policyn.
  - Märkning är byggd för `activities.source = 'garmin'` (migrering 024): `GarminAttribution.Sql` ger `attribution` ("Garmin [klockmodell]" för ägaren, bara "Garmin" för andra) under titeln i flöde, passlista och passsida samt i passsidans delvyer; `hasGarminData` i `/api/me` visar raden om härledd data på Statistik, egna mål och Utrustning. Nya vyer med Garmin-data ska ha samma märkning.
  - Garmin-data som visas för andra (flöde, profiler, delade pass) märks enligt Garmins brand guidelines (även vyer som bara ägaren ser). Nya sådana vyer anmäls med mockups till Garmin 30 dagar före lansering. Inga publika påståenden om Garmin utan deras skriftliga godkännande.
  - Ingen AI-träning, utvärdering eller AI-kunskapsbas på Garmin-data eller härledd data; riktig Garmin-data får inte klistras in i AI-verktyg. AI-bearbetning kräver uttryckligt samtycke och AI-redogörelse i policyn.
  - Bekräftade incidenter och allvarliga sårbarheter som rör Garmin-data anmäls till Garmin inom 24 timmar. Nyckeln kan dras in efter 6 månader utan användning.
- **Ingen anslutning till Stravas API.** Användarens egen arkivexport får importeras via ZIP; det kräver ingen Strava-anslutning.
- **Integritet/GDPR:** puls är hälsodata → uttryckligt samtycke. Pass privata som standard (`privacy = 'private'`), dolda start-/slutzoner på rutter, export och radering av konto från start. Personuppgiftsansvarig är användarens AB.
- Segment/topplistor à la Strava: avvakta, inte v1.
- **Enheter:** SI i databas och API (meter, sekunder, m/s; fältnamn med enhetssuffix som `distanceM`, `durationS`). Metriskt/imperial är ett visningsval per användare och konverteras bara i webben.
- **Data API är stängt:** migrering 003 återkallar `anon`/`authenticated` från allt i `public`, även framtida tabeller (default privileges). Lägg inte tillbaka grants; behövs direktåtkomst från webben senare, gör det medvetet med RLS-policies.
- **Milen är 1609,344 m.** `best_efforts.distance_m = 1609` är bara en etikett; rekordmotorn räknar med exakt längd.
- **Gratis, buret av supportrar:** all beräkning på användarens egen data (analys, statistik, rekord, export) är gratis och hamnar aldrig bakom betalvägg. Det som har verklig kostnad per användare (lagringstunga medier, externa API:er, AI) får generösa tak mot missbruk eller täcks av supportrar – inte en betalnivå med funktioner. Driften ska kunna bäras av frivilliga bidrag, så håll marginalkostnaden per användare nära noll:
  - Bilder skalas om i webbläsaren före uppladdning (omkodningen tar även bort EXIF-GPS) och serveras direkt från R2, inte via API:t.
  - Tunga jobb (Strava-import, omberäkning) går i kö med gränser per användare.
  - När databasen närmar sig den inkluderade disken: flytta tidsserierna till komprimerade filer i R2 och behåll sammanfattning, förenklad rutt och `best_efforts` i Postgres.
- **Supportermodell:** frivilligt årligt supporterskap, brons 50 kr, silver 150 kr och guld 300 kr per år, som årlig prenumeration (inte månadsvis – avgifterna äter små belopp). Valfritt belopp över 300 kr går att ge; det ger guldbadgen men inget mer, och driftaren får en notis för att kunna tacka personligen. Belöningen är enbart en badge på profilen och bredvid namnet. Nivån avslöjar belopp, så badgens synlighet är en inställning på Inställningar i stil med passens synlighet. Supporterskap ger aldrig funktioner. En öppen ekonomisida ska visa driftskostnad mot bidrag. Moms och redovisning stäms av innan lansering.

## Loggning och integritet
- Behåll `PrivateLogProvider` som API:ts enda loggprovider, även för start- och migreringsfel. Bara fasta händelser, granskade driftmått och projektionen i `LogException` får skrivas. Serialisera aldrig loggformatterare, godtyckligt state/scopes, råa undantag, felmeddelanden, absoluta källsökvägar eller requestuppgifter. Okända fält utelämnas. DbUp:s konsolloggning ska vara avstängd.
- Nya logghändelser eller loggmottagare kräver test med syntetiska känsliga värden. Direkt integration av exempelvis Sentry måste även granska automatisk exception-, request-, breadcrumb- och trace-insamling; loggprovidern skyddar inte sådana sidokanaler. Se README för omfattning.

## Säkerhet (XSS/CSRF)
- **CSRF:** sessionscookien är `SameSite=Lax` och alla skrivande `/api`-anrop kräver `X-CSRF-TOKEN`. GET-anrop får aldrig ändra data (undantagen är mejllänkarna `/api/auth/confirm`, som verifierar engångstoken utan att logga in, och `/api/auth/reset-password`, som skapar en återställningssession utan appåtkomst; själva lösenordsbytet kräver POST, samt OAuth-återkomsten `/api/garmin/callback`, som bara sparar anslutningen när state matchar en krypterad cookie för samma inloggade användare). Garmins push `/api/garmin/push` ligger utanför `/api`-gruppen utan session och CSRF och tar bara emot från Garmins IP-nät. Öppna inte CORS.
- **XSS:** tokens ligger i HttpOnly-cookien och går inte att stjäla, men ett injicerat skript kan ändå anropa API:t som användaren. Förhindra XSS: rendera användardata som text i React, aldrig `dangerouslySetInnerHTML` med användardata, inga `javascript:`-länkar från användardata.
- **CSP för webben** injiceras vid bygget i `web/vite.config.ts` (`script-src 'self'`, inga inline-skript eller `<style>`-taggar). Lägg till origins där när appen hämtar från nya ställen (t.ex. R2 för kartor) i stället för att lätta på reglerna. Kolla konsolen efter CSP-fel med `npm run build && npx vite preview` när beroenden läggs till – bibliotek som injicerar `<style>` behöver hanteras.
- **API-svar** har `default-src 'none'; frame-ancestors 'none'`, `nosniff` och `X-Frame-Options: DENY` (middleware i `Program.cs`, test i `SecurityHeadersTests`).
- **Där webben hostas** sätts som headers (går inte i meta-taggen): `Content-Security-Policy: frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` och HSTS. Servera webben och API:t från samma origin.

## Konventioner
- Appens typografiska grundskala finns i `web/src/index.css`: sidrubrik 24/32 px, avsnitt 20/28 px, underrubrik 16/24 px, brödtext 16/24 px och metadata 12/16 px (storlek/radhöjd vid standardinställning; rem låter användarens textstorlek slå igenom). Använd `Heading` i `web/src/components/ui/heading.tsx` med `level={1|2|3}` för motsvarande rubriknivå och halvfet stil; ange bara layoutklasser vid användningen. Använd vanliga HTML-element med `text-body` respektive `text-metadata` för brödtext och metadata. Formuläretiketter, kontroller och kompakt tabelltext behåller 14 px (`text-sm`); mätvärden får egen betoning. Migrera äldre kod när berörda vyer ändras. Den publika webbens typografi är separat.
- Tabellernas datarader har gemensam minsta höjd på 48 px via `tbody > tr` i `web/src/index.css`. Låt rader med mer innehåll växa naturligt.
- Alla input-, select- och textareafält använder `web/src/components/ui/form-field.tsx` (`FormField`) för gemensamt avstånd (8 px) och etikettkoppling via fältets genererade id. Standard är staplat; `layout="inline"` används för fält på samma rad och `layout="choice"` för checkboxar med etiketten efter kontrollen. `hideLabel` döljer etiketten visuellt men behåller dess tillgängliga namn. Valfri åtgärd bredvid etiketten anges med `action`.
- Brödsmulor visar hela sidans hierarki, inte bara närmaste förälder. Undersidor till Inställningar börjar med Profil → Inställningar.
- Knappar använder `Button` med varianterna `primary-filled` (förval, sidans huvudåtgärd), `secondary-filled`, `secondary-outline`, `ghost`, `destructive-outline` och `link` (bara understruken text). `className` får bara ange layout (marginal, bredd, placering); utseende kommer från varianten, vilket `web/tests/button.test.mjs` kontrollerar. Lägg till en variant i stället för att styla en enskild knapp.
- Modaler använder `web/src/components/ui/modal.tsx` (`Modal`). Bekräftelse före oåterkalleliga åtgärder använder `ConfirmationModal` i samma mapp, aldrig `window.confirm`. Klick utanför stänger som standard; ange `closeOnOutsideClick={false}` om ett flöde uttryckligen kräver annat. Befintliga `onCancel`-regler gäller även för klick utanför, exempelvis blockering under pågående sparande/radering.
- Appen har ännu inga användare och behöver inte vara bakåtkompatibel. Lägg inte till omdirigeringar, äldre API-format eller annan kompatibilitetskod för tidigare beteenden. Ompröva regeln när appen får användare.
- Engelska URL:er (`/app`, `/app/activities`, `/app/stats`, `/app/profile`, `/app/settings`), oberoende av valt språk.
- UI stödjer svenska och engelska med `react-i18next`. Lägg nya texter i båda `web/src/locales/{sv,en}.json` och använd typade `t()`-nycklar. Datum och tal formateras med valt språk via `Intl`; användardata översätts inte.
- Svenska får bara finnas i Markdown-filer. All kod är på engelska: kommentarer (även i SQL, skript, CSS och konfiguration), identifierare, loggar, testnamn och commit-meddelanden. Undantag är bara text som visas för användaren: `web/src/locales/sv.json`, API-felens `error`, mejlmallarna och de publika svenska sidorna. Körda migreringar ändras inte; nya migreringar skrivs på engelska.
- Språkprioritet: uttryckligt sparat val → svenskt IP → webbläsarens språk → engelska. IP är en ungefärlig signal från lokalt inbäddade IPv4-/IPv6-nät, aldrig ett åtkomstbeslut. Spara bara uttryckliga språkval.
- API-fel har svensk `error` och en stabil `code`; webben översätter koden vid rendering. Nya felkoder ska ha texter på båda språken. Mejlmallarna är tills vidare svenska.
- JSON i API:t är lowerCamelCase. Returnera typade records från Dapper, aldrig `dynamic`-rader (de serialiseras med snake_case-kolumnnamn som nycklar).
- Små, fokuserade commits. Följ verifieringen under Arbetsflöde innan commit.
